## Image sources

See the [ModelScope image build script](https://github.com/modelscope/modelscope/blob/build_swift_image/docker/build_image.py) for SWIFT image definitions. Tags include the operating system, CUDA, Python, PyTorch, vLLM, ModelScope, and SWIFT versions.

The v4 installation documentation lists this image in three regions:

```text
modelscope-registry.cn-hangzhou.cr.aliyuncs.com/modelscope-repo/modelscope:ubuntu22.04-cuda13.0.3-py312-torch2.13.0-vllm0.28.0-modelscope1.40.0-swift4.5.3
modelscope-registry.cn-beijing.cr.aliyuncs.com/modelscope-repo/modelscope:ubuntu22.04-cuda13.0.3-py312-torch2.13.0-vllm0.28.0-modelscope1.40.0-swift4.5.3
modelscope-registry.us-west-1.cr.aliyuncs.com/modelscope-repo/modelscope:ubuntu22.04-cuda13.0.3-py312-torch2.13.0-vllm0.28.0-modelscope1.40.0-swift4.5.3
```

Choose a nearby registry. This tag includes SWIFT 4.5.3; install SWIFT v5 inside the container to use it as a v5 base environment. Driver-dependent components must still be compatible with the host.

## Start a container

Install the NVIDIA driver, Docker, and NVIDIA Container Toolkit on the host. Mount model caches and training outputs persistently:

```bash
mkdir -p "$HOME/.cache/modelscope" "$PWD/output"
IMAGE=modelscope-registry.cn-hangzhou.cr.aliyuncs.com/modelscope-repo/modelscope:ubuntu22.04-cuda13.0.3-py312-torch2.13.0-vllm0.28.0-modelscope1.40.0-swift4.5.3
docker run --gpus all --ipc=host -it \
    -e MODELSCOPE_CACHE=/cache/modelscope \
    -v "$HOME/.cache/modelscope:/cache/modelscope" \
    -v "$PWD/output:/workspace/output" \
    -w /workspace \
    "$IMAGE" bash
```

Inside the container, run:

```bash
pip install 'ms-swift>=5.0.0'
```

Then run the [Quick Start](./quick-start.mdx) SFT or GRPO example. Install samplers, mathematical rewards, and other task dependencies as specified by the example.

## Server containers

Install server dependencies:

```bash
pip install 'twinkle-kit[server,client]'
```

Mount `server_config.yaml` and launch Ray and twinkle-server following [Remote Training](../interfaces/server-client.mdx). Access from other containers requires port mapping, a listening address, authentication, and a network entry point. A localhost-only configuration is not automatically exposed.

## Caches and resources

- Mount `MODELSCOPE_CACHE` persistently so weights survive container recreation. Also mount Hugging Face caches when using that hub.
- Mount the output directory containing checkpoints, logs, and metrics. A remote checkpoint URI is not a local path in the client container.
- `--ipc=host` uses host shared memory. Isolated deployments can configure separate shared memory; Ray and inference engines require sufficient capacity.
- Containers see only their allocated GPUs. Set `CUDA_VISIBLE_DEVICES` using device indices visible inside the container.
- Multi-node deployments need reachable inter-node networking and consistent model paths and versions. Using the same image does not automatically produce the same placement configuration.

AMD and NPU device mappings and runtimes differ. Follow the platform references in [Hardware Support](./installation.mdx).
